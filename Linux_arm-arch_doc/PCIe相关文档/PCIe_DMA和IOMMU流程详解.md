# PCIe DMA + IOMMU 访存流程图

本文档详细展示 PCIe 设备在有 DMA 和 IOMMU 的情况下如何访问系统内存的完整流程。

## 重要概念澄清

### 两种不同的寄存器

在 PCIe 系统里，有两种完全不同的寄存器：

1. **PCIe 配置空间寄存器（协议层）**：
   - 位置：PCIe 配置空间（0x00 ~ 0xFFF）
   - 内容：PCIe 规范定义的寄存器（Vendor ID、Device ID、BAR、Capability 等）
   - 用途：告诉系统"这是什么设备、有什么能力、BAR 在哪"
   - 访问方式：通过配置空间访问（Config TLP）
   - **这不是我们控制设备功能用的寄存器**

2. **设备功能寄存器（功能层，通过 BAR 映射）**：
   - 位置：BAR 映射的 MMIO 空间（如 BAR0 映射到 0xFEA00000）
   - 内容：**设备厂商自己定义的寄存器**（GPU 的控制寄存器、网卡的发送队列、NVMe 的命令队列等）
   - 用途：**控制设备功能、提交任务、查询状态**
   - 访问方式：通过 MMIO（Memory Read/Write TLP）
   - **这才是我们真正控制设备用的寄存器**

### 举例说明（GPU）

```
PCIe 配置空间（协议层，很少写）：
┌─────────────────────────┐
│ 0x00: Vendor ID         │ ← PCIe 规范定义（只读）
│ 0x02: Device ID         │ ← PCIe 规范定义（只读）
│ 0x10: BAR0 = 0xFEA00000 │ ← PCIe 规范定义（告诉系统 BAR 在哪）
│ 0x34: Capability Ptr    │ ← PCIe 规范定义（只读）
└─────────────────────────┘
     ↑
     这些是 PCIe 协议层的寄存器，不是用来控制 GPU 功能的

BAR0 映射空间（功能层，经常写）：
┌─────────────────────────┐
│ 0xFEA00000: GPU 控制寄存器 │ ← GPU 厂商自己定义（可写）
│ 0xFEA00004: GPU 状态寄存器 │ ← GPU 厂商自己定义（可读）
│ 0xFEA00010: 命令队列基址   │ ← GPU 厂商自己定义（可写）
│ 0xFEA00020: Doorbell     │ ← GPU 厂商自己定义（可写）
│ 0xFEA00030: DMA_SRC_ADDR │ ← GPU 厂商自己定义（可写）
│ 0xFEA00034: DMA_SIZE     │ ← GPU 厂商自己定义（可写）
└─────────────────────────┘
     ↑
     这些才是控制 GPU 功能的寄存器！我们一直在写的就是这些！
```

### 我们一直在写的是什么？

**我们一直在写的"设备寄存器"，实际上就是：**
- **GPU 的控制寄存器**（如果设备是 GPU）
- **网卡的发送队列寄存器**（如果设备是网卡）
- **NVMe 的命令队列寄存器**（如果设备是 NVMe SSD）
- **等等...**

**不是 PCIe 协议层的寄存器！**

### 为什么叫"PCIe 设备寄存器"？

- 因为它是"通过 PCIe 总线访问的设备寄存器"
- 但**这些寄存器是设备厂商自己定义的，不是 PCIe 规范定义的**
- PCIe 只是提供了"访问这些寄存器的通道"（通过 BAR 映射）

### 总结

- **PCIe 配置空间**：PCIe 协议层的寄存器，很少写，主要用于枚举和配置
- **BAR 映射空间**：设备功能层的寄存器，**这才是我们控制 GPU/网卡/NVMe 等设备功能用的寄存器**
- **我们一直在写的"设备寄存器" = BAR 映射空间里的寄存器 = GPU/网卡/NVMe 等设备的功能寄存器**

### BAR 的数量和映射内容：谁决定的？

#### 1. BAR 的数量：PCIe 规范规定

- **PCIe 规范规定**：每个 Function 最多有 **6 个 BAR**（BAR0 ~ BAR5）
- 这是规范强制规定的上限，所有 PCIe 设备都必须遵守
- 但设备可以只用其中几个（比如只用 BAR0 和 BAR2）

#### 2. 每个 BAR 映射什么内容：设备厂商在硬件设计时决定

- **这是设备厂商在 RTL 设计时就定死的**，不是软件写的
- 设备厂商在设计芯片时决定：
  - BAR0 映射什么（控制寄存器？命令队列？）
  - BAR1 映射什么（扩展寄存器？64bit BAR 的高位？）
  - BAR2 映射什么（显存？其他功能？）
  - 等等...

#### 3. 软件的作用：发现和分配地址

软件（BIOS/OS）只负责：

1. **发现 BAR**：
   - 读配置空间的 BAR 寄存器，知道设备有几个 BAR
   - 探测每个 BAR 需要多大空间（写全 1 再读回）

2. **分配系统物理地址**：
   - 给每个 BAR 分配一段系统物理地址空间
   - 把分配的地址写回 BAR 寄存器

3. **映射到虚拟地址**（驱动）：
   - 把 BAR 映射的物理地址映射到内核虚拟地址
   - 驱动就可以通过虚拟地址访问设备寄存器了

**软件不能改变 BAR 映射的内容！**

#### 举例说明（GPU）

```
设备厂商在设计 GPU 时（RTL 阶段）：
┌─────────────────────────────────────┐
│ 硬件设计决定：                       │
│                                     │
│ BAR0 → 映射到：控制寄存器 + 命令队列 │ ← 硬件设计时定死
│       大小：1MB                     │
│                                     │
│ BAR1 → 映射到：64bit BAR 的高 32 位 │ ← 硬件设计时定死
│       大小：4 bytes                 │
│                                     │
│ BAR2 → 映射到：显存（Frame Buffer） │ ← 硬件设计时定死
│       大小：256MB                   │
│                                     │
│ BAR3~BAR5 → 未使用                 │
└─────────────────────────────────────┘

软件（BIOS/OS）在枚举时：
┌─────────────────────────────────────┐
│ 1. 读配置空间，发现设备有 3 个 BAR   │
│ 2. 探测每个 BAR 需要多大：          │
│    - BAR0: 1MB                     │
│    - BAR1: 4 bytes                 │
│    - BAR2: 256MB                   │
│ 3. 分配系统物理地址：                │
│    - BAR0 → 0xFEA00000             │
│    - BAR1 → 0xFEA01000             │
│    - BAR2 → 0x80000000             │
│ 4. 写回 BAR 寄存器                  │
└─────────────────────────────────────┘

驱动在使用时：
┌─────────────────────────────────────┐
│ 1. 读 BAR 寄存器，得到物理地址       │
│ 2. 映射到虚拟地址                    │
│ 3. 访问设备寄存器（硬件设计时定死的）│
│    - BAR0 + 0x00: 控制寄存器        │
│    - BAR0 + 0x10: 命令队列          │
│    - BAR2 + 0x00000000: 显存        │
└─────────────────────────────────────┘
```

#### 关键点总结

- **BAR 数量**：PCIe 规范规定最多 6 个
- **BAR 映射内容**：设备厂商在硬件设计时决定，软件不能改变
- **软件的作用**：发现 BAR、分配系统物理地址、映射到虚拟地址
- **驱动的作用**：通过 BAR 映射的虚拟地址访问设备寄存器（这些寄存器是硬件设计时定死的）

#### 一句话总结

- **设备有几个 BAR、每个 BAR 映射什么内容，都是设备厂商在硬件设计时决定的，不是软件写的；软件只负责发现 BAR、分配系统物理地址、映射到虚拟地址，然后访问硬件设计时定死的那些寄存器。**

### CPU 和 GPU 之间的同步机制

#### 问题：CPU 写了 DMA 参数，GPU 怎么知道？

**关键点：CPU 写寄存器后，GPU 硬件能立即感知到！**

#### 同步机制 1：Doorbell（门铃机制）

```
CPU 侧（驱动）：
┌─────────────────────────────────────┐
│ 1. 准备数据（在系统内存里）          │
│    - 把要处理的数据放到内存 buffer  │
│    - 数据地址：0x80000000           │
│                                     │
│ 2. 配置 GPU DMA 参数                │
│    writel(0x80000000, gpu_regs + DMA_SRC_ADDR);
│    writel(4096, gpu_regs + DMA_SIZE);
│    │
│    └─> GPU 硬件立即感知到寄存器被更新！
│                                     │
│ 3. 敲 Doorbell（通知 GPU 有新任务） │
│    writel(0x1, gpu_regs + DOORBELL);
│    │
│    └─> GPU 硬件立即感知到 Doorbell 被敲！
│        │
│        └─> GPU 开始工作：
│            - 读 DMA_SRC_ADDR 寄存器
│            - 发起 DMA 读，从内存读数据
│            - 处理数据
│            - 完成后触发 MSI 中断
└─────────────────────────────────────┘
```

**Doorbell 的作用**：
- CPU 写 Doorbell 寄存器 = "敲 GPU 的门"
- GPU 硬件检测到 Doorbell 被写 = "听到敲门声"
- GPU 立即开始处理任务

#### 同步机制 2：轮询（Polling）

```
CPU 侧（驱动）：
┌─────────────────────────────────────┐
│ 1. 配置 GPU DMA 参数                │
│    writel(0x80000000, gpu_regs + DMA_SRC_ADDR);
│    writel(0x1, gpu_regs + DMA_START);
│    │
│    └─> GPU 硬件立即感知到，开始 DMA │
│                                     │
│ 2. CPU 轮询状态寄存器               │
│    while (1) {                      │
│        status = readl(gpu_regs + STATUS);
│        if (status & DMA_COMPLETE)   │
│            break;                   │
│        cpu_relax();  // 等待一下    │
│    }                                │
│    │
│    └─> CPU 不断读状态寄存器，直到 GPU 完成
└─────────────────────────────────────┘
```

#### 同步机制 3：中断（MSI/MSI-X）

```
CPU 侧（驱动）：
┌─────────────────────────────────────┐
│ 1. 配置 GPU DMA 参数                │
│    writel(0x80000000, gpu_regs + DMA_SRC_ADDR);
│    writel(0x1, gpu_regs + DMA_START);
│    │
│    └─> GPU 硬件立即感知到，开始 DMA │
│                                     │
│ 2. CPU 去做其他事情（不等待）        │
│    // 处理其他任务...               │
│                                     │
│ 3. GPU 完成 DMA 后，触发 MSI 中断   │
│    GPU → MSI → CPU                  │
│    │
│    └─> CPU 收到中断，调用中断处理函数
│        │
│        └─> 驱动检查状态，处理完成的数据
└─────────────────────────────────────┘
```

#### 关键点：硬件能立即感知寄存器变化

**为什么 GPU 能立即感知到 CPU 写寄存器？**

1. **CPU 写寄存器**：
   ```
   CPU → MMU → NoC → RC → PCIe 链路 → GPU
   ```

2. **GPU 硬件检测**：
   - GPU 内部的地址解码器识别：这是对某个寄存器的写
   - GPU 硬件逻辑立即更新内部状态
   - GPU 硬件逻辑检测到状态变化，触发相应动作

3. **GPU 开始工作**：
   - 如果写的是 DMA_START，GPU 立即开始 DMA
   - 如果写的是 Doorbell，GPU 立即检查命令队列

**这是硬件自动的，不需要软件通知！**

### GPU 内部的 DMA 引擎

#### GPU 确实有 DMA 引擎

**是的，GPU 内部有 DMA 引擎！** 这是 GPU 作为 PCIe 设备的核心功能之一。

#### GPU DMA 引擎的作用

GPU 内部的 DMA 引擎负责：

1. **从系统内存读取数据**：
   - 顶点数据、纹理数据、命令队列等
   - GPU 用 DMA 引擎发起 Memory Read TLP，从系统内存读取数据

2. **向系统内存写入数据**：
   - 渲染结果、计算结果等
   - GPU 用 DMA 引擎发起 Memory Write TLP，向系统内存写入数据

3. **自动管理传输**：
   - 根据配置的地址、长度，自动发起多次传输
   - 处理大块数据的传输（可能拆分成多个 TLP）

#### GPU DMA 引擎的结构

```
GPU 内部结构（简化）：
┌─────────────────────────────────────┐
│ GPU 核心功能                        │
│ - 渲染引擎                          │
│ - 计算单元                          │
│ - 纹理单元                          │
└─────────────────────────────────────┘
            ↑ ↓
┌─────────────────────────────────────┐
│ GPU 内部 DMA 引擎                   │ ← 这就是 GPU 的 DMA
│ - DMA 控制器                        │
│ - 地址/长度寄存器                   │
│ - 状态机                            │
│ - TLP 生成器                        │
└─────────────────────────────────────┘
            ↑ ↓
┌─────────────────────────────────────┐
│ PCIe 接口                           │
│ - PCIe 控制器                       │
│ - TLP 发送/接收                     │
└─────────────────────────────────────┘
            │
            └─> PCIe 链路
```

#### GPU DMA 工作流程

```
1. CPU 配置 GPU DMA 参数：
   writel(src_addr, gpu_regs + DMA_SRC_ADDR);  // 源地址
   writel(dst_addr, gpu_regs + DMA_DST_ADDR);  // 目的地址（可选）
   writel(size, gpu_regs + DMA_SIZE);          // 大小
   writel(0x1, gpu_regs + DMA_START);          // 启动

2. GPU DMA 引擎读取配置：
   GPU 内部的 DMA 控制器从寄存器读到：
   - 源地址：0x10000000 (IOVA)
   - 大小：4096 bytes
   - 启动标志：1

3. GPU DMA 引擎发起传输：
   GPU DMA 引擎自动：
   - 生成 Memory Read TLP
   - 地址：0x10000000
   - 长度：4096 bytes
   - 通过 PCIe 接口发送 TLP

4. 数据返回后：
   GPU DMA 引擎接收 Completion TLP
   - 数据写入 GPU 内部 buffer
   - 更新 DMA 状态寄存器
   - 触发 MSI 中断（如果配置了）
```

#### GPU DMA vs CPU DMA

| 特性 | GPU DMA | CPU DMA（片内 DMA IP） |
|------|---------|----------------------|
| 位置 | GPU 内部（PCIe 设备里） | SoC 内部（NoC 上的独立 IP） |
| 访问对象 | 系统内存（通过 PCIe） | 系统内存、外设寄存器（直接通过 NoC） |
| 协议 | PCIe TLP | AXI/CHI 事务 |
| 路径 | GPU → PCIe → RC → IOMMU → NoC → DDR | DMA → NoC → DDR |
| 用途 | GPU 读取/写入系统内存 | CPU 委托 DMA 搬运数据 |

#### 关键点

- **GPU 内部有 DMA 引擎**：这是 GPU 作为 PCIe 设备的标准功能
- **GPU DMA 通过 PCIe TLP**：GPU 用 Memory Read/Write TLP 访问系统内存
- **和 CPU DMA 的区别**：
  - GPU DMA：在 GPU 内部，通过 PCIe 访问系统内存
  - CPU DMA：在 SoC 内部，直接通过 NoC 访问系统内存
- **GPU DMA 是硬件自动的**：CPU 配置好参数后，GPU DMA 引擎自动工作

#### 一句话总结

- **GPU 内部确实有 DMA 引擎，负责通过 PCIe TLP 从系统内存读取数据或向系统内存写入数据；这是 GPU 作为 PCIe 设备的核心功能，和 CPU 的片内 DMA IP 是不同层面的概念。**

### 澄清：PCIe 和 GPU 的 DMA 关系

#### 关键概念区分

**PCIe 本身没有 DMA！**

- **PCIe** 是一个**协议/总线标准**，不是设备
- PCIe 只是定义了**如何通信**（TLP 格式、链路训练等）
- PCIe 本身不执行 DMA 操作

**GPU 有 DMA 引擎！**

- **GPU** 是一个 **PCIe 设备**（Endpoint）
- GPU 内部有 DMA 引擎，负责通过 PCIe 协议访问系统内存
- GPU 的 DMA 引擎使用 PCIe TLP 来传输数据

#### 架构关系

```
SoC 内部：
┌─────────────────────────────────────┐
│ Root Complex (RC)                   │
│ - PCIe 控制器                       │
│ - 协议转换（AXI ↔ PCIe TLP）        │
│ - 路由表                             │
│                                     │
│ 注意：RC 主要负责协议转换，         │
│      不叫"RC 的 DMA"                │
└─────────────────────────────────────┘
            │
            └─> PCIe 链路（协议层）
                │
                └─> PCIe 设备（如 GPU）
                    ┌─────────────────────────────────────┐
                    │ GPU 内部                             │
                    │ - GPU 核心功能                       │
                    │ - GPU DMA 引擎 ← 这才是 DMA！        │
                    │ - PCIe 接口                          │
                    └─────────────────────────────────────┘
```

#### 谁有 DMA？

| 组件 | 是否有 DMA | 说明 |
|------|-----------|------|
| **PCIe 协议** | ❌ 没有 | PCIe 是协议标准，不是设备 |
| **Root Complex (RC)** | ❌ 通常不这么说 | RC 主要负责协议转换，不叫"RC 的 DMA" |
| **GPU（PCIe 设备）** | ✅ 有 | GPU 内部有 DMA 引擎，通过 PCIe TLP 访问内存 |
| **网卡（PCIe 设备）** | ✅ 有 | 网卡内部有 DMA 引擎，通过 PCIe TLP 访问内存 |
| **NVMe SSD（PCIe 设备）** | ✅ 有 | NVMe 控制器内部有 DMA 引擎，通过 PCIe TLP 访问内存 |

#### 正确的理解

1. **PCIe 是"通道"**：
   - PCIe 提供了设备访问系统内存的"通道"
   - 但 PCIe 本身不执行 DMA

2. **设备有 DMA 引擎**：
   - GPU、网卡、NVMe 等 PCIe 设备内部有 DMA 引擎
   - 这些设备的 DMA 引擎使用 PCIe TLP 来传输数据

3. **RC 的作用**：
   - RC 负责把设备的 PCIe TLP 转换成 NoC/AXI 事务
   - RC 负责把 CPU 的 NoC/AXI 事务转换成 PCIe TLP
   - RC 是"翻译器"，不是 DMA 引擎

#### 完整的数据流

```
GPU DMA 引擎
    │
    └─> 生成 Memory Read TLP
        │
        └─> PCIe 链路（协议层，只是传输通道）
            │
            └─> Root Complex（协议转换）
                │
                └─> NoC → DDR（访问系统内存）
```

### GPU DMA 是否必须通过 PCIe？

#### 关键区分：访问系统内存 vs 访问 GPU 内部显存

**GPU DMA 访问系统内存：必须通过 PCIe！**

- GPU 是 PCIe 设备，系统内存在 SoC 内部（DDR）
- GPU 要访问系统内存，必须通过 PCIe 链路
- GPU DMA 引擎生成 PCIe TLP，通过 PCIe 链路访问系统内存

**GPU 访问自己的显存（VRAM）：不需要 PCIe！**

- GPU 内部有自己的显存（VRAM）
- GPU 核心访问显存是**内部操作**，不需要通过 PCIe
- GPU 内部有内部总线/互连，直接访问显存

#### GPU 内部架构示意

```
GPU 内部结构：
┌─────────────────────────────────────┐
│ GPU 核心功能                        │
│ - 渲染引擎                          │
│ - 计算单元                          │
│                                     │
│ 通过内部总线访问 ↓                  │
│                                     │
│ GPU 显存（VRAM）                    │ ← 内部访问，不需要 PCIe
│ - 帧缓冲区                          │
│ - 纹理缓存                          │
└─────────────────────────────────────┘
            │
            │ 通过 PCIe 访问 ↓
            │
┌─────────────────────────────────────┐
│ GPU DMA 引擎                         │
│ - 访问系统内存（DDR）                │ ← 必须通过 PCIe
│ - 通过 PCIe TLP 传输                 │
└─────────────────────────────────────┘
            │
            └─> PCIe 链路 → RC → NoC → DDR
```

#### 两种不同的数据流

**场景 1：GPU 访问系统内存（必须通过 PCIe）**

```
GPU DMA 引擎
    │
    └─> 生成 Memory Read TLP
        │
        └─> PCIe 链路 ← 必须通过！
            │
            └─> RC → NoC → DDR（系统内存）
```

**场景 2：GPU 访问自己的显存（不需要 PCIe）**

```
GPU 核心
    │
    └─> 通过内部总线
        │
        └─> GPU 显存（VRAM）← 内部访问，不需要 PCIe
```

#### 典型工作流程

```
1. CPU 准备数据在系统内存（DDR）
   │
   └─> 数据在系统内存：0x80000000

2. GPU DMA 从系统内存读取数据
   GPU DMA 引擎 → PCIe TLP → RC → NoC → DDR
   │
   └─> 数据从系统内存读到 GPU 内部 buffer

3. GPU 处理数据
   GPU 核心 → 内部总线 → GPU 显存（VRAM）
   │
   └─> 数据写入显存（内部操作，不需要 PCIe）

4. GPU 渲染/计算
   GPU 核心 ← 内部总线 → GPU 显存
   │
   └─> 从显存读取数据，执行渲染（内部操作）

5. GPU 把结果写回系统内存
   GPU DMA 引擎 → PCIe TLP → RC → NoC → DDR
   │
   └─> 渲染结果写回系统内存（必须通过 PCIe）
```

#### 关键点总结

- **GPU DMA 访问系统内存**：必须通过 PCIe（因为系统内存在 SoC 内部）
- **GPU 访问自己的显存**：不需要 PCIe（内部操作，通过内部总线）
- **GPU 内部数据流动**：不需要 PCIe（GPU 核心和显存之间的数据流动是内部操作）

#### 一句话总结

- **GPU DMA 访问系统内存时必须通过 PCIe，但 GPU 访问自己的显存时不需要 PCIe；GPU 内部的数据流动（核心 ↔ 显存）是内部操作，不需要 PCIe。**

#### 完整流程示例（GPU 渲染任务）

```
阶段 1: CPU 准备数据
─────────────────────
CPU:
1. 分配内存 buffer，准备渲染数据
2. 把数据写入内存（顶点数据、纹理等）

阶段 2: CPU 通知 GPU
─────────────────────
CPU:
1. 写 GPU 寄存器：命令队列地址、数据地址
   writel(cmd_queue_addr, gpu_regs + CMD_QUEUE_ADDR);
   writel(data_addr, gpu_regs + DATA_ADDR);
   │
   └─> GPU 硬件立即感知到寄存器被更新！

2. 写命令到命令队列（在系统内存里）
   cmd_queue[0] = {opcode: RENDER, ...};
   │
   └─> 命令在内存里，GPU 还不知道

3. 敲 Doorbell（通知 GPU 有新命令）
   writel(1, gpu_regs + DOORBELL);
   │
   └─> GPU 硬件立即感知到 Doorbell 被敲！
       │
       └─> GPU 开始工作：
           - 读命令队列地址寄存器
           - 发起 DMA 读，从内存读命令
           - 解析命令，知道要做什么
           - 发起 DMA 读，从内存读数据
           - 执行渲染
           - 完成后触发 MSI 中断

阶段 3: GPU 完成，通知 CPU
─────────────────────
GPU:
1. 渲染完成
2. 更新状态寄存器（在 GPU 内部）
3. 触发 MSI 中断

CPU:
1. 收到 MSI 中断
2. 调用中断处理函数
3. 读状态寄存器，知道 GPU 完成了
4. 处理结果数据
```

#### 总结

- **CPU 写寄存器后，GPU 硬件能立即感知到**（通过 PCIe 链路，硬件自动检测）
- **同步机制**：
  - **Doorbell**：CPU 敲 GPU 的门，GPU 立即响应
  - **轮询**：CPU 不断读状态寄存器，直到 GPU 完成
  - **中断**：GPU 完成后触发 MSI，CPU 异步处理
- **关键**：寄存器写操作是硬件可见的，GPU 硬件逻辑会自动检测并响应

6. 数据返回阶段：
   - 数据沿原路返回（不需要 IOMMU 翻译）
   - 设备接收数据，触发 MSI 中断

// 驱动代码（CPU 侧）
static int setup_pcie_dma_with_iommu(struct pci_dev *pdev, 
                                     void __user *user_buffer, 
                                     size_t size)
{
    dma_addr_t iova;  // IOVA（设备看到的地址）
    void *dma_buffer;
    
    // 1. 分配 DMA buffer（内核自动处理 IOMMU 映射）
    dma_buffer = dma_alloc_coherent(&pdev->dev, size, &iova, GFP_KERNEL);
    if (!dma_buffer)
        return -ENOMEM;
    
    // 此时：
    // - dma_buffer = 虚拟地址（CPU 可以访问）
    // - iova = IOVA（设备看到的地址，例如 0x10000000）
    // - 真实物理地址可能是 0x80000000，但设备不知道
    // - IOMMU 已自动建立映射：0x10000000 → 0x80000000
    
    // 2. 从用户空间拷贝数据
    if (copy_from_user(dma_buffer, user_buffer, size)) {
        dma_free_coherent(&pdev->dev, size, dma_buffer, iova);
        return -EFAULT;
    }
    
    // 3. 映射 BAR0（设备寄存器）
    void __iomem *dev_regs = pci_iomap(pdev, 0, 0);
    
    // 4. 配置 DMA（告诉设备 IOVA，不是物理地址）
    writel(lower_32_bits(iova), dev_regs + DMA_SRC_ADDR_LO);
    writel(upper_32_bits(iova), dev_regs + DMA_SRC_ADDR_HI);
    writel(size, dev_regs + DMA_SIZE);
    
    // 5. 启动 DMA
    writel(0x1, dev_regs + DMA_START);
    
    // 设备会用 IOVA 0x10000000 发起 DMA
    // IOMMU 会自动翻译成物理地址 0x80000000
    
    return 0;
}

// 中断处理函数（DMA 完成）
static irqreturn_t dma_complete_handler(int irq, void *dev_id)
{
    struct pci_dev *pdev = dev_id;
    void __iomem *dev_regs = pci_iomap(pdev, 0, 0);
    u32 status;
    
    // 读中断状态
    status = readl(dev_regs + INTERRUPT_STATUS);
    
    if (status & DMA_COMPLETE_BIT) {
        // DMA 完成，处理数据
        // ...
        
        // 清除中断
        writel(DMA_COMPLETE_BIT, dev_regs + INTERRUPT_STATUS);
    }
    
    return IRQ_HANDLED;
}

    │   ├─> 2.2.1 CPU 发起 MMIO 写
    │   │   地址：gpu_regs + GPU_DMA_SRC_ADDR（虚拟地址）
    │   │   数据：IOVA = 0x10000000
    │   │
    │   ├─> 2.2.2 MMU 翻译虚拟地址
    │   │   虚拟地址 → 物理地址 0xFEA00010（BAR0 + 偏移）
    │   │
    │   ├─> 2.2.3 CPU 发起 AXI/NoC 写事务
    │   │   地址：0xFEA00010
    │   │   数据：IOVA = 0x10000000
    │   │
    │   ├─> 2.2.4 NoC 路由
    │   │   查 SAM：0xFEA00010 落在哪个地址范围
    │   │   │
    │   │   └─> 匹配：0xFEA00000 ~ 0xFEA0FFFF → PCIe RC
    │   │
    │   ├─> 2.2.5 NoC 转发到 Root Complex
    │   │   AXI 写事务 → RC 的 AXI Slave 接口
    │   │
    │   ├─> 2.2.6 Root Complex 转换
    │   │   RC 识别：这是对 GPU BAR0 的访问
    │   │   RC 查路由表：地址 0xFEA00010 对应 GPU 的 BAR0
    │   │   │
    │   │   └─> 生成 Memory Write TLP
    │   │       - 目标：GPU (Bus:Dev:Func)
    │   │       - 地址：BAR0 内部偏移（0x0010）
    │   │       - 数据：IOVA = 0x10000000
    │   │
    │   ├─> 2.2.7 TLP 通过 PCIe 链路发送
    │   │   Memory Write TLP → PCIe 链路 → GPU
    │   │
    │   └─> 2.2.8 GPU 接收并更新寄存器
    │       │
    │       └─> GPU 内部地址解码：BAR0 + 0x0010 = DMA_SRC_ADDR 寄存器
    │           │
    │           └─> 寄存器被更新：DMA_SRC_ADDR = 0x10000000 (IOVA)
    │
    ├─> 2.3 写 GPU DMA 大小寄存器
    │   writel(4096, gpu_regs + GPU_DMA_SIZE);
    │   │
    │   └─> 同样的路径：CPU → NoC → RC → PCIe → GPU
    │       │
    │       └─> GPU 寄存器更新：DMA_SIZE = 4096
    │
    └─> 2.4 敲 Doorbell（启动 GPU DMA）
        writel(0x1, gpu_regs + GPU_DOORBELL);
        │
        └─> 同样的路径：CPU → NoC → RC → PCIe → GPU
            │
            └─> GPU 硬件检测到 Doorbell 被敲
                │
                └─> GPU 开始 DMA 读操作


阶段 3: GPU 发起 DMA 读请求（硬件自动）
─────────────────────────────────────────────────────────────────────

GPU (硬件自动)
    │
    ├─> 3.1 GPU 内部 DMA 引擎读取配置
    │   从 BAR0 映射的寄存器读到：
    │   - DMA_SRC_ADDR = 0x10000000 (IOVA)
    │   - DMA_SIZE = 4096
    │   - DOORBELL = 1（已启动）
    │
    ├─> 3.2 GPU 准备 Memory Read TLP
    │   │
    │   └─> TLP Header:
    │       ├─> Type: Memory Read
    │       ├─> Address: 0x10000000 (IOVA)
    │       ├─> Length: 4096 bytes
    │       ├─> Requester ID: GPU (Bus:Dev:Func)
    │       └─> Tag: 0x01（用于匹配响应）
    │
    └─> 3.3 GPU 发送 Memory Read TLP
        │
        └─> TLP 通过 PCIe 链路发送 → Root Complex


阶段 4: Root Complex 处理（硬件自动）
─────────────────────────────────────────────────────────────────────

PCIe Root Complex (RC)
    │
    ├─> 4.1 RC 接收 Memory Read TLP
    │   识别：这是 GPU 发起的 DMA 读请求
    │   地址：0x10000000 (IOVA)
    │   长度：4096 bytes
    │   来源：GPU (Bus:Dev:Func)
    │
    └─> 4.2 RC 转发到 IOMMU（如果启用）
        │
        └─> 如果 IOMMU 未启用：
            └─> 直接跳到步骤 5.1（用物理地址）


阶段 5: IOMMU 地址翻译（硬件自动）
─────────────────────────────────────────────────────────────────────

IOMMU (Input-Output Memory Management Unit)
    │
    ├─> 5.1 IOMMU 接收 DMA 请求
    │   地址：0x10000000 (IOVA)
    │   设备：GPU (Bus:Dev:Func)
    │   操作：Memory Read
    │
    ├─> 5.2 IOMMU 查页表
    │   查找：IOVA 0x10000000 对应的物理地址
    │   │
    │   └─> 页表命中：IOVA 0x10000000 → PA 0x80000000
    │
    ├─> 5.3 IOMMU 权限检查
    │   检查：GPU 是否有权限访问这个 IOVA
    │   │
    │   └─> 权限检查通过（驱动已经 map 了这个区域）
    │
    └─> 5.4 IOMMU 输出翻译后的地址
        │
        └─> 输出：物理地址 PA = 0x80000000
            │
            └─> 转发到 NoC


阶段 6: NoC 路由（硬件自动）
─────────────────────────────────────────────────────────────────────

NoC (Network-on-Chip)
    │
    ├─> 6.1 NoC 接收访问请求
    │   地址：0x80000000 (物理地址)
    │   类型：Memory Read
    │   长度：4096 bytes
    │   来源：PCIe RC（来自 GPU）
    │
    ├─> 6.2 NoC 查地址映射表（SAM）
    │   查找：0x80000000 落在哪个地址范围
    │   │
    │   └─> 匹配：0x80000000 ~ 0x8FFFFFFF → DDR0 控制器
    │
    ├─> 6.3 NoC 路由决策
    │   如果配置了 hash range：
    │   - 对地址做 hash 运算
    │   - 决定走哪个 DDR 通道
    │   │
    │   └─> 路由到：DDR0 控制器
    │
    └─> 6.4 NoC 转发请求
        │
        └─> AXI/CHI 读事务 → DDR 控制器


阶段 7: DDR 控制器访问内存（硬件自动）
─────────────────────────────────────────────────────────────────────

DDR 控制器
    │
    ├─> 7.1 DDR 控制器接收请求
    │   地址：0x80000000 (物理地址)
    │   类型：Read
    │   长度：4096 bytes
    │   来源：NoC（来自 GPU）
    │
    ├─> 7.2 DDR 控制器地址解码
    │   地址：0x80000000
    │   │
    │   ├─> 确定：Bank、Row、Column
    │   │
    │   └─> 生成：DDR 读命令序列
    │
    ├─> 7.3 DDR 控制器访问 DDR 芯片
    │   │
    │   └─> DDR 命令 → DDR 芯片
    │       │
    │       └─> DDR 芯片执行读操作
    │           │
    │           └─> 从物理地址 0x80000000 读取 4096 bytes
    │
    └─> 7.4 DDR 芯片返回数据
        │
        └─> 数据：4096 bytes（顶点数据、纹理等）


阶段 8: 数据返回路径（硬件自动）
─────────────────────────────────────────────────────────────────────

DDR 芯片
    │

阶段 9: GPU 接收数据（硬件自动）
─────────────────────────────────────────────────────────────────────

GPU
    │
    ├─> 9.1 GPU 接收 Memory Read Completion TLP
    │   识别：这是对之前 Memory Read 请求的响应

    │

    │   │

    │       status = readl(gpu_regs + STATUS_REG);

    │           │

    │

        │
        └─> 驱动可以继续下一步操作
            - 处理 GPU 处理后的数据
            - 提交下一个任务
            - 等等...

数据流路径总结
═══════════════════════════════════════════════════════════════════════

CPU 配置 GPU（写寄存器）：
CPU → MMU → NoC → RC → PCIe 链路 → GPU

GPU 读取系统内存（DMA 读）：
GPU → PCIe 链路 → RC → IOMMU → NoC → DDR 控制器 → DDR 芯片

数据返回 GPU：
DDR 芯片 → DDR 控制器 → NoC → IOMMU → RC → PCIe 链路 → GPU

GPU 通知 CPU（MSI 中断）：
GPU → PCIe 链路 → RC → NoC → APIC → CPU


═══════════════════════════════════════════════════════════════════════
关键点总结
═══════════════════════════════════════════════════════════════════════

1. CPU 准备数据：
   - 在系统内存（DDR）里准备数据
   - 分配 IOVA（如果启用 IOMMU）
   - IOMMU 建立映射：IOVA → 物理地址

2. CPU 配置 GPU：
   - 通过 BAR 写 GPU 寄存器，告诉 GPU 数据地址（IOVA）
   - GPU 硬件立即感知到寄存器被更新

3. GPU 发起 DMA 读：
   - GPU 用 IOVA 发起 Memory Read TLP
   - RC 转发到 IOMMU

4. IOMMU 翻译：
   - IOMMU 把 IOVA 翻译成物理地址
   - 做权限检查

5. NoC 路由：
   - NoC 根据物理地址查 SAM，路由到 DDR 控制器
   - 可能做 hash 打散到多个 DDR 通道

6. DDR 访问：
   - DDR 控制器访问 DDR 芯片
   - 读取数据

7. 数据返回：
   - 数据沿原路返回（不需要 IOMMU 翻译）
   - GPU 接收数据

8. GPU 通知 CPU：
   - GPU 处理完成后，触发 MSI 中断
   - CPU 收到中断，处理完成事件
