# PCIe 电源管理与链路低功耗

> D-state / L-state / ASPM / PME / STR 全景，含简历"STR 总线挂死"案例的机制背景。详细排查过程见 [总线挂死修复](../../../07_面试/简历打磨/总线挂死修复.md)。

## 1. 两套状态：设备 D-state 与链路 L-state

### 设备电源状态（D0-D3）

| 状态 | 含义 | 唤醒 |
|---|---|---|
| D0 | 全速工作 | - |
| D1/D2 | 中间态（可选支持） | PME |
| D3hot | 仍可响应配置 TLP | PME |
| D3cold | 主电断（仅 aux 电） | PME（需 wake#） |

### 链路电源状态（ASPM，链路两侧协商）

| 状态 | 省电 | 恢复延迟 |
|---|---|---|
| L0 | - | - |
| L0s | 小（单向 standby） | 极短（~ns） |
| L1 | 中（双向 standby，时钟可停） | 短 |
| L1 子状态（L1.1/L1.2） | 大（关 common mode/refs） | 稍长 |
| **L2/L3 Ready** | 链路准备下电 | 需走 Recovery 恢复 |

- ASPM L0s/L1 由硬件自动协商进出（`pcie_aspm=off` 可关）；L2 是系统级 S3/STR 时链路真正下电
- **进出这些状态都是协议报文握手**，不是直接断电--这就是 PME_Turn_Off 案例的机制根源

## 2. 睡眠/唤醒的协议序列（STR/S3）

```
suspend 路径：
设备驱动 suspend -> pci_prepare_to_sleep() -> 目标 D-state
  -> 若需唤醒：使能 PME（PME_En + 设备 Power Management 的 wake 位）
  -> 端口序列：
     1. RC 广播 PM_PME_Message Deny / Assert？
     2. 下游口发 PME_Turn_Off Message（消息码 0x19）
     3. 设备回 PME_TO_Ack
     4. 链路进 L2/L3 Ready，关时钟/电源

resume 路径：
上电 -> PERST# -> LTSSM 重新训练（Detect->...->L0）
  -> 配置空间恢复（BAR/MSI Table 全是易失的，驱动/PCI core 保存恢复）
  -> 设备可发 PME（若它先于系统醒来）或正常恢复
```

### 案例：PME_Turn_Off 消息码错误导致总线挂死

简历/项目实例：Cadence IP 在 STR 路径发错了消息码（0x15 而非 0x19），设备等不到合法的 Turn_Off 握手，链路卡在过渡态，resume 后总线上所有设备消失。修复：改消息码 + L2_IDLE 状态轮询 + 低功耗前 quiesce 所有中断源。

教训（面试口径）：
- **低功耗路径的 bug 症状在 resume 后才显形**（挂死/设备消失），根因却常在 suspend 序列
- Message TLP 不占地址空间、只有 type，配错仍"能发出去"所以平时不炸
- 三件套修复：协议修正 + 状态确认（轮询而非盲延迟）+ 中断静默（防握手期间中断改状态）

## 3. PME（Power Management Event）：唤醒信号

- 设备在低电状态下想唤醒系统：发 **PME Message**（或拉 WAKE# 引脚）-> RC -> 平台电源管理逻辑
- 驱动侧：`device_init_wakeup(dev, true)` + `pci_pme_active()`；平台侧 DT/ACPI 的 wakeup 描述
- 调试：`/sys/bus/pci/devices/.../power/wakeup`、`cat /proc/acpi/wakeup`（ACPI 平台）

## 4. 内核 API 速查

| API | 作用 |
|---|---|
| `pci_set_power_state(dev, state)` | D-state 切换（写 PMCSR） |
| `pci_prepare_to_sleep` / `pci_resume` | suspend/resume 封装（选目标态+PME 配置） |
| `pci_save_state` / `pci_restore_state` | 配置空间保存/恢复（含 BAR、MSI） |
| `pci_wake_from_d3` | 使能/关闭 D3 唤醒 |
| `pcie_aspm` 内核参数 | `off`/`performance`/`powersave`/`default` |

## 5. 调试

| 现象 | 查 |
|---|---|
| resume 后设备消失（lspci 空） | suspend 序列是否走完（Turn_Off 握手/时钟关断时序）、resume 后 PERST/LTSSM 日志 |
| 偶发唤醒失败 | PME 是否使能、WAKE# 路由、设备是否真进目标 D 态 |
| 低功耗后性能变差 | ASPM L1 进出频繁：`pcie_aspm=off` 对照，powertop 看链路驻留 |
| suspend 卡死 | `echo devices_suspend` 阶段卡：某驱动 suspend 回调不返回；ftrace `pci_*` + `pm_suspend` 时间线 |

## 6. 面试问答

**Q: L0s/L1/L2 区别？**
L0s 单向 standby 恢复最快；L1 双向时钟停、省电更多；L2 链路下电，恢复要重新训练（系统级睡眠才用）。ASPM 管 L0s/L1（硬件自动），L2 是软件流程（含 Turn_Off 握手）。

**Q: 为什么 STR 前要 quiesce 中断？**
握手/下电窗口内设备若再产生 MSI/DMWr，落在已关闭的窗口地址上会挂总线或丢失；先静默再下电保证状态机单一。

**Q: D3cold 和 D3hot 的 BAR 状态？**
都丢。D3hot 配置空间还在（可恢复访问），D3cold 连配置空间都要靠 firmware/驱动重建；`pci_save/restore_state` 只兜配置空间，BAR 重映射由 PCI core 在 resume 重跑。

**Q: ASPM 会不会引起兼容性问题？**
会，链路两侧时钟容忍度不同（common clock 误判）、部分设备 L1 退出有 bug；内核维护 ASPM 黑名单，排查性能/稳定性问题时先关 ASPM 对照。
