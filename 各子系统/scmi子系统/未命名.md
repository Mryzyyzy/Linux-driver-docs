### KMS 显示管线

```
Framebuffer → Plane → CRTC → Encoder → Connector → 物理显示器
```

- **Plane**：图层（primary/overlay/cursor），负责 scanout framebuffer
- **CRTC**：扫描引擎，驱动时序生成，混合多个 Plane
- **Encoder**：信号格式转换（数字→HDMI/DP/LVDS 等）
- **Connector**：物理接口，负责热插拔检测（HPD）、EDID 读取

典型驱动分层：
- **平台驱动**：处理设备探测、时钟、电源域

## Dumb Buffer 与 mmap

### Dumb Buffer 是什么

Dumb Buffer 是 DRM 子系统提供的一种**最简单的显存分配方式**——它只是一块连续的、无硬件加速的内存区域。与 GPU 渲染用的 GEM buffer 不同，dumb buffer：

- 不经过 GPU 管线，无法做硬件加速绘图
- 仅用于 **CPU 直接读写像素**（软件渲染）
- 通常用于 framebuffer console、splash screen、简单 UI、测试工具等场景

### 为什么需要 mmap

内核流程中各步骤的层次：

```
DRM_IOCTL_MODE_CREATE_DUMB
  → 在内核空间分配一块物理内存（显存/CMA/系统内存）
  → 返回 handle（内核侧句柄），用户空间拿不到地址

drmModeAddFB(handle)
  → 将这块内存注册为 Framebuffer 对象
  → 显示控制器（CRTC）可以从这里 scanout

DRM_IOCTL_MODE_MAP_DUMB
  → 为该 buffer 创建一个 mmap offset
  → 返回 offset，但此时还没有映射

mmap(fd, offset)
  → 将内核空间的物理内存映射到用户空间虚拟地址
  → 用户进程拿到指针，可以直接写像素
```

**关键问题**：`CREATE_DUMB` 分配的内存在**内核地址空间**，用户态进程无法直接访问。`mmap` 的作用就是在用户进程的虚拟地址空间中建立一个到该物理内存的映射，拿到一个可用的指针。

```c
// mmap 之后，buf 就是用户空间可用的指针
uint32_t *buf = mmap(0, size, PROT_READ | PROT_WRITE, MAP_SHARED, fd, offset);

// 直接写像素，例如填充红色（XRGB8888）
for (int i = 0; i < width * height; i++)
    buf[i] = 0x00FF0000;
```

### 完整数据流

```
用户空间                         内核空间                      硬件
───────                         ────────                     ────
CREATE_DUMB ──ioctl──→  分配物理内存 page[]
                                  ↑
MAP_DUMB    ──ioctl──→  创建 mmap offset
                                  ↑
mmap()      ─────────→  建立 VA → PA 页表映射
                                  
buf[i]=pixel ─────────→  CPU 直写物理内存
                                  ↓
               AddFB ──→ 注册为 FB 对象
              SetCrtc ──→ CRTC scanout ──→  显示控制器从该地址读取像素 → 屏幕
```

简单说：**dumb buffer 是显存，mmap 是让用户态程序能直接往显存里画像素的桥梁**。没有 mmap，用户态只有一个 handle 数字，无法写入任何数据。

GitHub Copilot: Optimized tool selection不是严格意义上的“映射关系”，更准确说：**mmap offset 是一个给用户态 `mmap()` 使用的索引/钥匙，用来让 DRM 驱动在后续 mmap 调用中找到要映射的那个 buffer**。

在 dumb-buffer 流程里有两步容易混：

```c
drmIoctl(fd, DRM_IOCTL_MODE_MAP_DUMB, &map);
mmap(NULL, size, PROT_READ | PROT_WRITE, MAP_SHARED, fd, map.offset);
```

`DRM_IOCTL_MODE_MAP_DUMB` 做的是：

1. 根据 dumb buffer 的 `handle` 找到内核里的 GEM buffer 对象；
2. 为这个 buffer 准备一个可以被 `mmap()` 识别的 fake offset；
3. 把这个 offset 返回给用户态。

这个 offset **不是物理地址**，也不是用户虚拟地址，通常也不是文件里的真实偏移。它更像 DRM/GEM 内部维护的一个“cookie”。

真正建立映射关系的是后面的：

```c
mmap(..., fd, map.offset);
```

当用户态调用 `mmap()` 时，内核会看到：

- 你 mmap 的文件描述符是 `/dev/dri/card0`
- 你传入的 offset 是 `map.offset`

然后 DRM 驱动根据这个 offset 查找到对应的 GEM/dumb buffer，再把这块 buffer 的页映射到当前进程的虚拟地址空间里。此时才真正建立：

```text
用户态虚拟地址  ->  dumb buffer 对应的物理页/内存页
```

可以理解成：

```text
CREATE_DUMB
  创建 buffer，得到 handle

MAP_DUMB
  handle -> mmap offset
  只是生成“mmap 入口编号”

mmap
  offset -> buffer
  建立用户虚拟地址到 buffer 内存页的映射
```

所以一句话：**创建 mmap offset 不是建立最终内存映射，而是为后续 `mmap()` 建立一个可查找的入口；真正的 VA 到 buffer 页的映射发生在 `mmap()` 系统调用里。**

### 一、整体调用链

```text
用户态 mmap(fd, offset)
   │
   ▼
sys_mmap → mmap_region → call_mmap()
   │
   ▼
file->f_op->mmap()           ← DRM 字符设备的 mmap 钩子
   │
   ▼
drm_gem_mmap()               ← DRM core
   │
   ▼
obj->funcs->mmap()  或  drm_gem_mmap_obj()
   │
   ▼  （设置 vma 标志、vm_ops）
vma->vm_ops = &drm_gem_shmem_vm_ops / drm_gem_cma_vm_ops ...
   │
   ▼  （此时还没真正映射页，仅设置好"懒映射"基础设施）
返回用户态，得到一个 VA
   │
   ▼  用户态首次访问 buf[i] → 缺页异常
do_page_fault → handle_mm_fault → __do_fault
   │
   ▼
vma->vm_ops->fault()  →  实际把 page 填入页表
```

关键点：**`mmap()` 系统调用本身通常只设置 VMA（虚拟内存区域）和 fault 钩子，并不立即建立页表，真正的 PA↔VA 绑定是在缺页时由 `vm_ops->fault()` 完成的。**

### 二、入口：DRM 字符设备的 mmap

DRM 设备的 file_operations：

```c
// drivers/gpu/drm/drm_file.c (简化)
static const struct file_operations drm_stub_fops = {
    .mmap   = drm_gem_mmap,
    ...
};
```

`drm_gem_mmap()` 做的事：

```c
int drm_gem_mmap(struct file *filp, struct vm_area_struct *vma)
{
    struct drm_file *priv = filp->private_data;
    struct drm_gem_object *obj;

    /* 1. 用 vma->vm_pgoff (就是 MAP_DUMB 返回的那个 offset >> PAGE_SHIFT)
     *    去 drm_vma_offset_manager 里查找对应的 GEM 对象        */
    node = drm_vma_offset_lookup_locked(dev->vma_offset_manager,
                                        vma->vm_pgoff,
                                        vma_pages(vma));
    obj = container_of(node, struct drm_gem_object, vma_node);

    /* 2. 调用具体驱动/后端的 mmap，设置 vm_ops */
    return drm_gem_mmap_obj(obj, obj->size, vma);
}
```

这就是上一轮说的 **"offset 是个 cookie"** 的兑现点：内核拿 `vm_pgoff` 反查到 GEM 对象。

### 三、具体后端：以 shmem helper 为例

大多数 dumb buffer 走的是 **shmem helper**（`drm_gem_shmem_helper.c`）或 **CMA helper**。看 shmem：

```c
// drivers/gpu/drm/drm_gem_shmem_helper.c
const struct vm_operations_struct drm_gem_shmem_vm_ops = {
    .fault  = drm_gem_shmem_fault,
    .open   = drm_gem_shmem_vm_open,
    .close  = drm_gem_shmem_vm_close,
};

int drm_gem_shmem_mmap(struct drm_gem_shmem_object *shmem,
                       struct vm_area_struct *vma)
{
    vma->vm_flags |= VM_MIXEDMAP | VM_DONTEXPAND;
    vma->vm_page_prot = pgprot_writecombine(vm_get_page_prot(vma->vm_flags));
    vma->vm_ops = &drm_gem_shmem_vm_ops;
    return 0;   /* 注意：没有真正映射任何页 */
}
```

注意 `pgprot_writecombine` —— 显存/framebuffer 通常用 WC（write-combine）属性，避免 CPU 缓存导致显示控制器看到旧数据。

### 四、缺页处理：把真实物理页塞进页表

用户态写 `buf[i] = pixel` 时，第一次访问该页会触发缺页：

```c
static vm_fault_t drm_gem_shmem_fault(struct vm_fault *vmf)
{
    struct vm_area_struct *vma = vmf->vma;
    struct drm_gem_object *obj = vma->vm_private_data;
    struct drm_gem_shmem_object *shmem = to_drm_gem_shmem_obj(obj);
    pgoff_t page_offset;
    struct page *page;

    page_offset = (vmf->address - vma->vm_start) >> PAGE_SHIFT;

    /* 取出该 buffer 在 page 数组中的对应物理页 */
    page = shmem->pages[page_offset];

    /* 把 page 插入到当前进程页表，建立 VA -> PFN 映射 */
    return vmf_insert_pfn(vma, vmf->address, page_to_pfn(page));
}
```

到这一步，进程页表里才真正有了：

```text
进程VA  ── PTE ──►  物理页 PFN（dumb buffer 的某一页）
```

之后 CPU 读写这段 VA 就是直接读写显存。

### 五、那这些 `page` 是哪里来的？是否涉及伙伴系统？

**取决于 buffer 后端**，这是核心：

#### 1. shmem 后端（最常见 dumb buffer 实现）

```c
// drm_gem_shmem_helper.c (简化)
static int drm_gem_shmem_get_pages(struct drm_gem_shmem_object *shmem)
{
    struct drm_gem_object *obj = &shmem->base;
    struct page **pages;

    pages = drm_gem_get_pages(obj);   /* 内部走 shmem_read_mapping_page */
    shmem->pages = pages;
    return 0;
}
```

`drm_gem_get_pages()` → `shmem_read_mapping_page_gfp()` → tmpfs/shmem 子系统分配页。tmpfs 底层最终调用 **`alloc_pages()` / `alloc_page()`，这就是伙伴系统（buddy allocator）**。但每次只要一个 order-0 页，不要求物理连续。

```text
shmem_read_mapping_page
    └─► shmem_alloc_folio
        └─► folio_alloc
            └─► __alloc_pages   ← 伙伴系统入口
```

特点：物理上**不连续**，每页独立从 buddy 拿；通过页表把它们拼成连续 VA。

#### 2. CMA 后端（很多嵌入式/ARM SoC 的 dumb buffer，如显示控制器需要连续物理地址）

```c
// drivers/gpu/drm/drm_gem_dma_helper.c (旧名 cma)
struct drm_gem_dma_object *
drm_gem_dma_create(struct drm_device *drm, size_t size)
{
    dma_obj->vaddr = dma_alloc_wc(drm->dev, size,
                                  &dma_obj->dma_addr,
                                  GFP_KERNEL | __GFP_NOWARN);
    ...
}
```

`dma_alloc_wc()` 在有 CMA 的系统上会走 **CMA 分配器**（`cma_alloc()`），CMA 是从预留的连续物理内存区里切一块出来，**不直接走伙伴系统**（但 CMA 区域本身是在启动时从 memblock 预留的，平时这片区域的页对 buddy 是"借给 movable 用"的，分配 CMA 时再回收）。

回退路径（没有 CMA 或小块）会用 `alloc_pages()` 直接从伙伴系统拿高阶连续页（`__GFP_DMA32` 等）。

#### 3. VRAM/独显后端

物理显存由 PCI BAR 暴露，驱动通过 `ttm` 管理，不经过伙伴系统，映射时用 `vmf_insert_pfn` 直接写 PCI MMIO 的 PFN。

### 六、对应到 CIX/linlon-dp 这类显示驱动

像你在看的显示驱动，扫描的 framebuffer 一般要求**物理连续 + 特定对齐**（DMA 引擎拿物理地址直读）。因此 dumb buffer 后端基本是 **CMA / DMA coherent**，分配路径是：

```text
CREATE_DUMB
  → drm_gem_dma_dumb_create
    → dma_alloc_wc / dma_alloc_coherent
      → CMA 或 buddy（高阶连续页）

MAP_DUMB
  → drm_gem_create_mmap_offset
    → 在 vma_offset_manager 注册一个 fake offset

mmap(fd, offset)
  → drm_gem_mmap → drm_gem_dma_mmap
    → remap_pfn_range(vma, ..., dma_addr >> PAGE_SHIFT, size, WC)
```

注意 CMA 后端常用 **`remap_pfn_range()` 一次性建表**（因为物理连续），不需要 fault handler 一页页填，与 shmem 的懒映射不同。

### 七、总结一张图

```text
┌─────────────────────────── 用户态 ───────────────────────────┐
│   mmap(fd, off) ──────────► VA 区间 (VMA)                    │
│      首次访问 buf[i] ─┐                                       │
└───────────────────────┼───────────────────────────────────────┘
                        ▼ 缺页 / 或 mmap 时一次性建表
┌──────────────────── 内核 DRM/GEM ────────────────────────────┐
│  vm_pgoff ──► drm_vma_offset_manager ──► GEM object          │
│  vm_ops->fault() / remap_pfn_range() ──► 写进程页表          │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────── buffer 后端（决定页从哪来） ─────────────────┐
│  shmem  ──► shmem_alloc_folio ──► __alloc_pages  (伙伴系统)  │
│  CMA    ──► cma_alloc                 (预留连续区，非 buddy) │
│  TTM/VRAM ► PCI BAR PFN               (不分配，直接用 MMIO)  │
└──────────────────────────────────────────────────────────────┘
```

**结论**：

- `mmap()` 通过 `vm_pgoff` 这个 cookie 反查到 GEM 对象，然后设置 VMA 和 `vm_ops`，**真正的页表填充发生在缺页**（shmem 路径）或 **mmap 时 `remap_pfn_range` 一次性建立**（CMA/连续物理路径）。
- **是否涉及伙伴系统取决于后端**：shmem 后端最终走 `__alloc_pages`，是伙伴系统；CMA 后端走 CMA 分配器（独立于 buddy 的预留区）；VRAM 后端不分配系统内存。

```text
   │                                                         │
   │  drmModeAddFB(...handle..., &fb_id)                     │
   │     └─ 把这块显存包装成 DRM "Framebuffer 对象" → fb_id   │
   │        (CRTC 只认 fb_id，不直接认 handle)               │
   │                                                         │
   │  DRM_IOCTL_MODE_MAP_DUMB → mmap                         │
   │     └─ 让 CPU 能写像素                                  │
   │                                                         │
   │  memset(vaddr, 0xff, size)                              │
   │     └─ 往显存里画内容(填白)                             │
   └─────────────────────────────────────────────────────────┘
                     │  → 提供 fb_id (有内容的 framebuffer)
                     ▼
   ┌──────────────────────────────────────────────────────────┐
   │  drmModeSetCrtc(fd, crtc_id, fb_id, 0, 0,                │
   │                 &conn_id, 1, &conn->modes[0])            │
   │                  │       │       │            │          │
   │                  │       │       │            └ 显示模式 │
   │                  │       │       └ Connector ID 列表     │
   │                  │       └ FB ID                         │
   │                  └ CRTC ID                               │
   │                                                          │
   │   内核：                                                 │
   │     1. 配置 CRTC 时序为 mode 指定的 (clock/htotal/...)   │
   │     2. 让 CRTC 的 primary plane 指向 fb_id 的物理地址    │
   │     3. 路由 CRTC → Encoder → Connector                   │
   │     4. 上电 / 打开输出 → 图像出现在屏幕上               │
   └──────────────────────────────────────────────────────────┘
                     │
                     ▼
              getchar()  ← 阻塞，让画面停留
                     │
                     ▼
   modeset_destroy_fb : RmFB → munmap → DESTROY_DUMB
   drmModeFreeConnector / FreeResources / close   ← 释放资源
```

### 参数对应关系一句话总结

| `drmModeSetCrtc` 参数 | 来源函数 |
|------------------------|----------|
| `fd` | `open("/dev/dri/card0")` |
| `crtc_id` | `drmModeGetResources()` → `res->crtcs[0]` |
| `conn_id` | `drmModeGetResources()` → `res->connectors[0]` |
| `fb_id` | `drmModeAddFB()`（其内部 buffer 来自 `CREATE_DUMB`） |
| `mode` | `drmModeGetConnector()` → `conn->modes[0]` |
| `x, y` | 字面量 0,0（在 FB 内的扫描起始坐标） |

所以**前面所有 ioctl/库调用，都是在凑齐 SetCrtc 需要的这几个 ID 和模式**；`mmap + memset` 则是为了让显示出去时画面不是空的。

## 二、四个前提条件解析

### 1. DRM 驱动支持 MODESET

**MODESET = Kernel Mode Setting (KMS)**，即显示模式（分辨率、刷新率、时序）由内核驱动直接配置硬件，而不是由用户态（如旧的 X Server UMS）去操作寄存器。

判断方式 —— 驱动注册时声明 feature flag：

```c
static const struct drm_driver my_drm_driver = {
    .driver_features = DRIVER_MODESET | DRIVER_GEM | DRIVER_ATOMIC,
    ...
};
```

没有 `DRIVER_MODESET`，`drmModeGetResources()` 这类 KMS ioctl 直接失败，整个 demo 跑不起来。**只用作 GPU 渲染（render-only）的驱动不带 MODESET**，例如 `/dev/dri/renderD128`。

### 2. DRM 驱动支持 dumb-buffer

Dumb buffer 是 KMS 提供的"傻瓜显存分配"接口，要求驱动实现：

```c
struct drm_driver {
    int (*dumb_create)(struct drm_file *file, struct drm_device *dev,
                       struct drm_mode_create_dumb *args);
    int (*dumb_map_offset)(...);   /* 可选，默认实现可用 */
    ...
};
```

显示控制器通过 DMA 直接读 framebuffer 物理地址扫描像素，因此 dumb buffer 几乎都是**物理连续**的（CMA / DMA coherent / 预留 VRAM）。如果驱动没实现 `dumb_create`：

```c
drmIoctl(fd, DRM_IOCTL_MODE_CREATE_DUMB, &create);  // 返回 -ENOSYS / -EINVAL
```

那就拿不到 buffer，后续 `AddFB / SetCrtc` 都无从谈起。部分纯渲染驱动（如 Mesa 走 GBM 的场景）不需要 dumb buffer，但也跑不了这个 demo。

### 3. 至少 1 个 CRTC、1 个 Encoder、1 个 Connector

这是 KMS 显示管线的三个核心对象，构成一条完整的"出图链路"：

```text
Framebuffer ──► [Plane] ──► CRTC ──► Encoder ──► Connector ──► 显示器
                            │         │           │
                  扫描时序生成器  信号格式转换器  物理接口/HPD/EDID
                  (RGB流+VSYNC)  (RGB→DP/HDMI/   (DP/HDMI座、
                                   MIPI/LVDS)     LVDS排线)
```

- **CRTC (CRT Controller)**：扫描引擎，按 mode 时序从 framebuffer 抓像素、产生像素流和同步信号
- **Encoder**：把 CRTC 输出的并行 RGB 数据编码成具体物理协议（TMDS/DP 主链路/MIPI DSI 等）
- **Connector**：代表一个物理接口，负责热插拔检测、读取 EDID、提供该显示器支持的 modes 列表

`drmModeSetCrtc()` 内核实现里要做的事情包括："给定 connector → 找一个能驱动它的 encoder → 绑定到这个 CRTC"。如果三者中任一为零：

- 没 CRTC：没人去扫 framebuffer，画面无法产生
- 没 Encoder：CRTC 信号无法转成可被接口传输的格式
- 没 Connector：内核不知道接什么显示器、用什么模式

`res->crtcs[0]` / `res->connectors[0]` 也会越界。

### 4. Connector 至少有 1 个有效的 `drm_display_mode`

`drmModeModeInfo` 描述一组完整的显示时序：

```c
struct drm_mode_modeinfo {
    __u32 clock;          // 像素时钟 kHz
    __u16 hdisplay, hsync_start, hsync_end, htotal, hskew;
    __u16 vdisplay, vsync_start, vsync_end, vtotal, vscan;
    __u32 vrefresh;
    __u32 flags;          // 同步极性、interlace 等
    __u32 type;           // PREFERRED / DRIVER / USERDEF ...
    char  name[DRM_DISPLAY_MODE_LEN];
};
```

Mode 通常有两个来源：

1. **EDID**：Connector 探测时读取显示器 EDID，解析出它声明支持的所有分辨率/刷新率，填到 `connector->modes` 链表
2. **驱动内建**：如固定面板（eDP/LVDS panel）通过 device tree / panel driver 提供固定 mode

demo 直接用了：

```c
buf.width  = conn->modes[0].hdisplay;
buf.height = conn->modes[0].vdisplay;
...
drmModeSetCrtc(..., &conn->modes[0]);
```

如果 `conn->count_modes == 0`（例如：HDMI 没插显示器、EDID 读失败、panel 驱动未提供 mode），`conn->modes[0]` 是非法访问，且 `SetCrtc` 没有合法时序可用，CRTC 无法启动扫描，屏幕也不会亮。

可通过 `drmModeGetConnector()` 返回的 `connection` 字段判断：

```c
if (conn->connection != DRM_MODE_CONNECTED || conn->count_modes == 0)
    /* 不能直接用 modes[0] */
```

### 小结

- 其他函数都是**为 `drmModeSetCrtc` 凑齐 4 个参数**（CRTC ID、FB ID、Connector ID、Mode）以及**给 FB 填上像素**。
- 四个前提条件本质是 KMS 流水线 `FB → Plane → CRTC → Encoder → Connector → Mode` 这条链路必须**端到端可用**：MODESET 提供 API、dumb-buffer 提供 FB 内存、CRTC/Encoder/Connector 提供硬件路径、Mode 提供时序参数，缺一不可。

User: fd, offset对应的是页和偏移量吗

GitHub Copilot: 不是。**`fd` 不是页号，`offset` 也不是页内偏移量**。它们是 `mmap()` 系统调用的参数，含义完全不同。

## 一、`mmap` 的签名与参数含义

```c
void *mmap(void *addr, size_t length, int prot, int flags,
           int fd, off_t offset);
```

| 参数 | 含义 |
|------|------|
| `fd` | **文件描述符**，指向一个打开的文件/设备（这里是 `/dev/dri/card0`）。告诉内核"映射的是哪个对象" |
| `offset` | **在该 fd 对应对象内部的字节偏移**。要求**页对齐**（通常是 4KB 的倍数） |

所以是 **"对象 + 对象内偏移"** 的二元组，而不是"页号 + 页内偏移"。

## 二、和"页 + 页内偏移"的区别

操作系统里"页 + 页内偏移"通常指的是 MMU 的虚拟地址分解：

```text
虚拟地址 VA = [   VPN (页号)   |  page offset (页内偏移 12bit)  ]
                       │
                       ▼ 通过页表
              物理地址 PA = [ PFN | page offset ]
```

这是 **CPU 访问内存时硬件做的事**，发生在 `mmap` 返回指针之后、每次访存时。

而 `mmap(fd, offset)` 的 `offset` 是**字节单位的文件/设备内偏移**，跟 MMU 的 page offset 不是一个东西。

## 三、在 DRM dumb buffer 场景中的特殊性

```c
drmIoctl(fd, DRM_IOCTL_MODE_MAP_DUMB, &map);   // map.offset 是内核生成的"假"偏移
mmap(0, size, PROT_READ|PROT_WRITE, MAP_SHARED, fd, map.offset);
```

这里的 `map.offset` 表面上是"`/dev/dri/card0` 内的字节偏移"，但实际上 **DRM 设备并没有真的 N 字节大的文件**。这个 offset 是 DRM 的 `drm_vma_offset_manager` 在一个虚拟地址空间里分配出来的一段范围，专门作为查找 GEM 对象的"键"。

进入内核后：

```c
int drm_gem_mmap(struct file *filp, struct vm_area_struct *vma)
{
    /* offset 转成页号，去查 GEM 对象 */
    node = drm_vma_offset_lookup_locked(dev->vma_offset_manager,
                                        vma->vm_pgoff,   //  = offset >> PAGE_SHIFT
                                        vma_pages(vma));
    obj = container_of(node, struct drm_gem_object, vma_node);
    ...
}
```

注意这里 `vma->vm_pgoff = offset >> PAGE_SHIFT`，**这个右移只是因为 VMA 内部用页号存储 offset 更紧凑**，是字节偏移到页号的换算，并不代表"用户传的 offset 是页号"。

## 四、对比一下三个容易混的"offset"

| 概念 | 单位 | 出现位置 | 作用 |
|------|------|----------|------|
| `mmap` 的 `offset` 参数 | **字节**（页对齐） | 用户态系统调用 | 标识 fd 对象内的位置/cookie |
| `vma->vm_pgoff` | **页**（PAGE_SIZE 为单位） | 内核 VMA 结构 | 上面那个 offset 的页号形式 |
| MMU 虚拟地址里的 page offset | **字节**（低 12 bit） | 硬件 MMU | 页内定位具体字节 |

## 五、一句话总结

`mmap(fd, offset)` 的 `(fd, offset)` 是 **"映射哪个对象 + 在该对象里从哪个字节开始"**，不是"页号 + 页内偏移"。在 DRM 里这个 `offset` 还退化成了纯粹的查找键（cookie），用来反查 GEM 对象。**真正的"页 + 页内偏移"是 MMU 在你访问 `mmap` 返回的指针时自动做的事，跟 mmap 参数没关系。**

GitHub Copilot: ## `O_RDWR | O_CLOEXEC` 含义

这是 `open()` 的 `flags` 参数，用按位或组合多个标志。

### `O_RDWR` — 读写模式打开

`open()` 必须指定三种访问模式之一：

| 标志 | 含义 |
|------|------|
| `O_RDONLY` | 只读 |
| `O_WRONLY` | 只写 |
| `O_RDWR` | **读写** |

DRM 设备需要：
- **写**：发送 ioctl 配置 CRTC、写 framebuffer 数据
- **读**：读取硬件状态、读 EDID、读返回的 buffer 元数据

所以必须 `O_RDWR`。如果只用 `O_RDONLY` 打开 `/dev/dri/card0`，大部分 KMS ioctl 会因权限不够直接失败。

### `O_CLOEXEC` — close-on-exec

在该 fd 上设置 **FD_CLOEXEC 标志**：当当前进程调用 `execve()` 启动一个新程序时，**这个 fd 会被内核自动关闭，不会泄漏给子进程**。

```c
fd = open("/dev/dri/card0", O_RDWR | O_CLOEXEC);
// ... 后续 fork + execve("/bin/some_tool", ...)
// 新程序里看不到这个 fd
```

不加的话默认行为是：

```c
fd = open("/dev/dri/card0", O_RDWR);
// fork + exec → 子进程仍然拥有这个 fd（甚至能继续操作显示控制器！）
```

#### 为什么要加？

1. **安全**：避免敏感设备/资源的 fd 泄漏到不受控的子程序，尤其是 DRM master 权限的 fd 被泄漏意味着子进程能抢占显示控制
2. **资源**：避免子进程持有 fd 导致父进程关闭后内核对象仍未释放
3. **避免竞态**：与"先 `open()` 再 `fcntl(fd, F_SETFD, FD_CLOEXEC)`"相比，`O_CLOEXEC` 是**原子**的——后者在多线程环境下，`open` 与 `fcntl` 之间若发生 `fork+exec`，fd 仍会泄漏

### 等价写法

```c
// 推荐（原子）
fd = open(path, O_RDWR | O_CLOEXEC);

// 老写法（有竞态窗口，不推荐）
fd = open(path, O_RDWR);
fcntl(fd, F_SETFD, FD_CLOEXEC);
```

### 小结

- `O_RDWR`：以读写方式打开 DRM 设备节点，满足 ioctl/mmap 双向访问需求
- `O_CLOEXEC`：fork+exec 时自动关闭该 fd，防泄漏、防权限扩散，是现代 Linux 系统编程的**默认推荐做法**

几乎所有 DRM/GBM/EGL 示例代码都会这样写，属于惯用法。

GitHub Copilot: ## `execve()` 触发场景

`execve()` 是 Linux 中**用新程序替换当前进程映像**的系统调用。当前进程的代码、数据、堆栈被新程序覆盖，但**进程 ID、打开的文件描述符等内核资源默认保留**（除非设置了 `O_CLOEXEC`）。

通常配合 `fork()` 使用，这是 Unix 创建并运行新程序的经典模式：**fork + exec**。

### 一、典型场景

#### 1. Shell 执行命令

你在终端输入 `ls`：

```text
bash 进程
  ├─ fork()           ← 复制出一个子进程（仍然是 bash 副本）
  └─ 子进程:
       execve("/bin/ls", ["ls"], envp)   ← 把自己变成 ls 程序
```

bash 自己不会变成 ls，而是 fork 出一个子进程让它 exec 成 ls。

#### 2. `system()` / `popen()` 库函数

```c
system("convert input.png output.jpg");
```

底层就是 fork + execve("/bin/sh", "-c", "convert ...")。

#### 3. C 代码显式调用 `exec` 家族

```c
pid_t pid = fork();
if (pid == 0) {
    execlp("ffmpeg", "ffmpeg", "-i", "in.mp4", "out.mp4", NULL);
    _exit(1);  // exec 失败才会执行到这
}
waitpid(pid, NULL, 0);
```

`execl/execlp/execv/execvp/execle/execve` 都是 `execve` 的包装。

#### 4. 守护进程 / 服务管理器启动子服务

systemd、supervisord、init 启动每个服务都是 fork + execve。

#### 5. GUI 程序启动外部工具

例如浏览器调用外部 PDF 阅读器，编辑器调用外部 diff 工具，IDE 调用 gcc 编译等等。

#### 6. 容器运行时启动容器内进程

`docker run`、`runc`、`crun` 启动容器进程时也是 fork + execve（在 namespace 隔离之后）。

### 二、与 DRM `O_CLOEXEC` 相关的具体风险场景

假设一个合成器（如 Weston/KWin）打开了 `/dev/dri/card0` 拿到 DRM master，然后它要启动一个截图工具：

```c
int drm_fd = open("/dev/dri/card0", O_RDWR);  // 没加 O_CLOEXEC

if (fork() == 0) {
    execve("/usr/bin/screenshot-tool", argv, envp);
    // 子进程现在是 screenshot-tool
    // 但它继承了 drm_fd —— 子进程也能操作显示控制器！
}
```

更典型的例子：

- **桌面环境启动应用**：GNOME Shell / KWin fork+exec 一个用户点击的应用程序，如果不加 `O_CLOEXEC`，该应用会继承合成器的所有 fd（DRM、Wayland socket、输入设备等）
- **登录管理器启动会话**：gdm/sddm fork+exec 用户 shell 时
- **X server / 合成器调用外部 helper**：调用 `xkbcomp`、`gdbus` 等
- **多媒体框架 fork 编解码进程**：GStreamer 启动 helper

如果合成器内任何一个 `open()` 忘了加 `O_CLOEXEC`，被启动的子程序就有可能：

- 持有 DRM master fd，能抢占屏幕控制
- 持有 input event fd，能读所有键盘鼠标输入（键盘记录器风险）
- 持有 socket，能冒充合成器与客户端通信

### 三、什么时候**不会**触发 execve

很多场景你以为有"启动新程序"，其实没用 execve：

- **动态库 dlopen**：在当前进程里加载，不是新程序，不触发 execve
- **线程创建 pthread_create**：仅创建线程，进程映像不变
- **`fork()` 但不 exec**：子进程依然运行原程序（如多进程服务的 worker）
- **`posix_spawn()`**：内部仍是 fork+exec，只是封装了，**同样受 `O_CLOEXEC` 影响**
- **`vfork() + exec`**：行为类似，**同样受影响**

### 四、一句话总结

**只要进程要"启动另一个可执行文件"，就一定会经过 `execve`**（无论是直接调用还是通过 `system/popen/posix_spawn/fork+exec` 包装）。对长期运行、持有敏感 fd 的程序（如显示合成器、登录管理器、守护进程），**默认所有 `open()` 都应加 `O_CLOEXEC`**，否则任何一次 exec 都可能造成 fd 泄漏。

## 一、`execve()` 后哪些东西保留 / 不保留

| 资源 | 默认行为 | 是否受 `O_CLOEXEC` 影响 |
|------|----------|--------------------------|
| **进程 PID** | 保留（同一个进程，只是换了程序） | ❌ 永远保留，与 `O_CLOEXEC` 无关 |
| **父进程 PPID** | 保留 | ❌ 无关 |
| **打开的 fd（普通）** | 保留 | ✅ 设置后 exec 时关闭 |
| **打开的 fd（带 `O_CLOEXEC`）** | exec 时关闭 | —— |
| 内存映像（代码/堆/栈） | **被新程序覆盖** | ❌ 无关 |
| 信号处理函数 | 重置为默认 | ❌ 无关 |
| 当前工作目录 | 保留 | ❌ 无关 |
| umask、资源限制 | 保留 | ❌ 无关 |

## 二、`O_CLOEXEC` 的精确作用域

`O_CLOEXEC` 是**每个 fd 独立的属性**（FD_CLOEXEC 标志），存在该 fd 的 file descriptor flags 里。它只决定：

> **当本进程调用 `execve()` 时，内核要不要把这个 fd 自动 close 掉。**

不会影响：
- 进程本身（PID 不变）
- 其他 fd（每个 fd 各自独立的标志）
- 父子关系
- 任何其他内核资源

## 三、举例

```c
int a = open("/tmp/a", O_RDWR);              // 无 O_CLOEXEC
int b = open("/tmp/b", O_RDWR | O_CLOEXEC);  // 有 O_CLOEXEC

printf("我的 pid=%d\n", getpid());           // 比如 1234

execve("/bin/some_prog", argv, envp);
// ──── 分割线 ────
// 现在进程的"代码"是 /bin/some_prog
// pid 仍然是 1234（不变！）
// fd a：仍然打开，some_prog 能用
// fd b：已经被内核关闭，some_prog 看不到
```

## 一、关键点：`execve` 不创建新进程

`execve()` 是**在同一个进程内**用新程序替换旧程序的代码和数据。它**没有 fork，没有新进程**。所以：

```text
execve 之前：进程 1234 在跑你的 C 代码，拥有 fd a 和 fd b
execve 之后：进程 1234 在跑 some_prog 的代码，仍然是同一个进程
              → 这个进程的 fd 表 也是同一张表
```

**fd 表是进程的属性**，进程没变，fd 表就还在。新程序继承的就是这张表里的所有 fd。

## 二、`/tmp/a`、`/tmp/b`、fd、some_prog 的关系

把它们分清楚：

| 概念 | 含义 |
|------|------|
| `/tmp/a`、`/tmp/b` | 磁盘上的**文件** |
| fd `a`、fd `b` | 进程 fd 表里的**条目**（小整数 + 内核 file 对象指针） |
| `some_prog` | 被加载进当前进程的**程序代码** |

```text
进程 1234 的 fd 表：
   fd 3 ──► 内核 file 对象 ──► inode(/tmp/a)
   fd 4 ──► 内核 file 对象 ──► inode(/tmp/b)   [FD_CLOEXEC=1]
```

`execve("/bin/some_prog", ...)` 时，内核做的事：

1. 把进程 1234 的内存映像替换成 some_prog 的 ELF（代码段、数据段全换掉）
2. **遍历 fd 表**，把每个带 `FD_CLOEXEC` 的 fd 关掉
3. 跳到 some_prog 的入口开始执行

结果：

```text
进程 1234（现在跑的是 some_prog 代码）的 fd 表：
   fd 3 ──► 内核 file 对象 ──► inode(/tmp/a)     ← 仍然存在
   fd 4 ──── 已关闭 ────                           ← 因为 O_CLOEXEC
```

## 三、"关闭的不是 /tmp/b 吗，怎么和 some_prog 扯上关系？"

关闭的**不是磁盘文件** `/tmp/b`（文件还在磁盘上，谁都没动它），而是**进程 1234 里指向 `/tmp/b` 的那个 fd（条目）**。

而 some_prog 现在就是运行在进程 1234 里的代码，**它能看到的所有 fd 就是这张 fd 表里剩下的 fd**。所以：

- fd 3（指向 /tmp/a）还在 → some_prog 在自己的代码里可以 `read(3, ...)`、`write(3, ...)`，**它操作的就是 /tmp/a 这个文件**
- fd 4 已经被内核 close 掉 → some_prog 想 `read(4, ...)` 会得到 `EBADF`，**它根本不知道 /tmp/b 曾经被打开过**

换句话说：

> **fd 是进程的"通行证"。进程 1234 之前用 fd 4 能访问 /tmp/b；execve 之后还是进程 1234，但 fd 4 被收走了，所以现在跑的 some_prog 就没法访问 /tmp/b 了。文件本身没变，变的是"谁手里还攥着访问凭证"。**

## 四、回到 DRM 场景的实际意义

```c
int drm_fd = open("/dev/dri/card0", O_RDWR);              // 不带 CLOEXEC
fork() → 子进程 execve("/usr/bin/some_tool", ...);
```

- `/dev/dri/card0` 这个设备节点当然不会被"删除"
- 但**子进程的 fd 表里继承了 drm_fd**，于是 `some_tool` 这个本不该碰显示控制器的程序，现在手里拿着一个能操作 DRM 设备的 fd —— 它可以 ioctl 改显示模式、读 framebuffer 等

加上 `O_CLOEXEC` 后：

- 设备节点 `/dev/dri/card0` 还是在那
- 但子进程的 fd 表里那一项被内核 close 掉了，`some_tool` 没有 fd，就没法访问 DRM 设备

GitHub Copilot: 下面分别介绍 `crtc_id`、`connector_id`、`fb_id`、`drm_mode` 这几个参数在 DRM/KMS 显示流程中的作用：

---

### 1. `crtc_id`（CRTC 控制器 ID）

- **全称**：CRT Controller（扫描时序控制器）
- **作用**：负责从 framebuffer 里读取像素，生成显示时序信号（如 VSYNC、HSYNC、DE），并驱动后端的 Encoder/Connector。
- **在 `drmModeSetCrtc` 里**：指定要配置哪个 CRTC 单元（一个 SoC/显卡可能有多个 CRTC，支持多屏独立输出）。
- **决定**：哪个显示通道负责把 framebuffer 的内容送到指定的物理输出。

---

### 2. `connector_id`（连接器 ID）

- **全称**：Connector（物理输出接口）
- **作用**：代表一个物理显示接口，如 HDMI、DP、eDP、LVDS、VGA 等，负责热插拔检测、EDID 读取、管理显示模式列表。
- **在 `drmModeSetCrtc` 里**：指定要把 CRTC 的输出连接到哪个物理接口（可以是一个或多个）。
- **决定**：最终画面会输出到哪个显示器/屏幕。

---

### 3. `fb_id`（Framebuffer ID）

- **全称**：Framebuffer（帧缓冲对象）
- **作用**：描述一块显存区域，存放要显示的像素数据（如 XRGB8888 格式），由用户空间分配并注册到 DRM。
- **在 `drmModeSetCrtc` 里**：指定 CRTC 要扫描/显示的那块 framebuffer。
- **决定**：屏幕上实际显示的内容是哪块内存的数据。

---

### 4. `drm_mode`（显示模式）

- **类型**：`drmModeModeInfo` 结构体
- **作用**：描述一组完整的显示时序参数（分辨率、刷新率、同步信号、像素时钟等），通常来源于显示器 EDID 或面板驱动。
- **在 `drmModeSetCrtc` 里**：指定 CRTC 要用哪种显示模式（如 1920x1080@60Hz）。
- **决定**：屏幕的分辨率、刷新率、时序等硬件参数。

---

### 总结关系

- `crtc_id`：选哪个显示通道（负责扫描/输出）
- `fb_id`：选哪块显存作为显示内容
- `connector_id`：输出到哪个物理接口/显示器
- `drm_mode`：用什么分辨率/刷新率/时序参数

它们共同决定了**“哪块内容、以什么方式、通过哪个通道、输出到哪个屏幕”**。

```c
static int linlondp_gem_dma_dumb_create(struct drm_file *file,
                                        struct drm_device *dev,
                                        struct drm_mode_create_dumb *args)
{
    struct linlondp_dev *mdev = dev->dev_private;
    u32 pitch = DIV_ROUND_UP(args->width * args->bpp, 8);

    args->pitch = ALIGN(pitch, mdev->chip.bus_width); // 按硬件总线宽度对齐
    return drm_gem_dma_dumb_create_internal(file, dev, args); // 走 CMA
}
```

**要点**：
- 它没自己分配内存，调用通用的 `drm_gem_dma_dumb_create_internal`，最终走 **CMA / dma_alloc_wc** —— 这就是上几轮我们说的"显示控制器需要物理连续"
- 重写它只是为了按 `bus_width` 做 pitch 对齐（硬件 DMA 要求）

## 二、逐条解释

### ① DRIVER_MODESET —— 驱动的能力声明

这是内核驱动在注册时主动声明的：

```c
// linlondp_kms.c
static struct drm_driver linlondp_kms_driver = {
    .driver_features = DRIVER_GEM | DRIVER_MODESET | DRIVER_ATOMIC,
    ...
};
```

应用程序无法"添加"这个能力。如果驱动没声明（例如 render-only 驱动 renderD128），所有 KMS ioctl 都会失败，应用最多能做的是检测后报错退出。

### ② dumb-buffer —— 驱动实现的可选回调

由驱动决定要不要实现：

```c
// linlondp_kms.c
DRM_GEM_DMA_DRIVER_OPS_WITH_DUMB_CREATE(linlondp_gem_dma_dumb_create),
```

应用可以检测：

```c
uint64_t has_dumb;
drmGetCap(fd, DRM_CAP_DUMB_BUFFER, &has_dumb);
if (!has_dumb) { /* 走 GBM 或别的分配路径 */ }
```

但**无法让驱动"突然支持"**。

### ③ CRTC / Encoder / Connector 数量

这是**硬件物理限制 + 驱动实现**的结果：

- SoC 显示控制器有几条扫描通道 → 决定 CRTC 数量
- SoC 集成了哪些输出 IP（DP/DSI/HDMI） → 决定 Encoder 数量
- 板子上接了几个物理接口 → 决定 Connector 数量

驱动注册这些对象：

```c
// linlondp_kms_attach 里大致流程
drm_crtc_init_with_planes(...)      // 注册 CRTC
drm_encoder_init(...)               // 注册 Encoder
drm_connector_init(...)             // 注册 Connector
```

应用程序通过 `drmModeGetResources()` 枚举出来后只能"用现有的"，不可能凭空创造一个 CRTC。

### ④ Connector 有有效的 display mode

mode 的来源两种：

- **显示器 EDID**：插上 HDMI/DP 显示器后，内核驱动通过 DDC/AUX 通道读 EDID，解析出该显示器支持的所有 mode，挂到 `connector->modes`
- **驱动内建**：固定面板（eDP/LVDS/MIPI）没有 EDID，驱动或 panel driver 在 device tree 里写死 mode

应用程序的角色：

```c
conn = drmModeGetConnector(fd, conn_id);
if (conn->connection != DRM_MODE_CONNECTED || conn->count_modes == 0) {
    // 没插显示器 / EDID 失败 / panel 没 mode —— 应用只能放弃
}
// 选一个 mode 用
drmModeSetCrtc(..., &conn->modes[0]);
```

如果**显示器没插**或 **EDID 读不出来**，连应用都救不了，得用户去插线或换显示器。

## 一、函数逐层剖析

### 调用背景

在 linlondp_drv.c 里：

```c
err = aperture_remove_all_conflicting_devices("linlondp");
```

目的：在自家 DRM 驱动 bind 之前，**把之前占用同一段显存（framebuffer aperture）的"占位驱动"踢掉**，避免冲突。典型的"占位驱动"是：

- **efifb / vesafb / simplefb / simpledrm**：BIOS/UEFI 阶段把固件 framebuffer 暴露给内核，让你在启动早期就能看到 logo
- 当真正的 GPU/DP 驱动加载时，必须先卸载这些占位驱动，自己接管显存

### 第 0 层：入口（inline wrapper）

文件：include/linux/aperture.h

```c
static inline int aperture_remove_all_conflicting_devices(const char *name)
{
    return aperture_remove_conflicting_devices(0, (resource_size_t)-1, name);
}
```

- 只是个 inline 包装，传入 `[0, ~0]` 这个**覆盖整个物理地址空间**的范围
- 等价于"不管在哪里的 framebuffer aperture，全踢掉"

### 第 1 层：`aperture_remove_conflicting_devices`

文件：aperture.c

```c
int aperture_remove_conflicting_devices(resource_size_t base, resource_size_t size,
                                        const char *name)
{
    sysfb_disable(NULL);                      // ① 阻止 sysfb 之后再注册占位驱动
    aperture_detach_devices(base, size);      // ② 真正干活：把现有占位驱动卸载
    return 0;
}
```

两件事：

1. **`sysfb_disable()`**：sysfb（system framebuffer）是负责注册 efifb/vesafb/simplefb/simpledrm 等"固件 framebuffer 平台设备"的子系统。调用它防止以后再创建新占位设备。
2. **`aperture_detach_devices()`**：从已注册的 aperture 列表中，把和 `[base, base+size)` 重叠的所有占位设备卸载掉。

### 第 2 层：`aperture_detach_devices`

```c
static void aperture_detach_devices(resource_size_t base, resource_size_t size)
{
    resource_size_t end = base + size;
    struct list_head *pos, *n;

    mutex_lock(&apertures_lock);

    list_for_each_safe(pos, n, &apertures) {                    // ① 遍历全局 aperture 链表
        struct aperture_range *ap = container_of(pos, struct aperture_range, lh);
        struct device *dev = ap->dev;

        if (WARN_ON_ONCE(!dev))
            continue;

        if (!overlap(base, end, ap->base, ap->base + ap->size)) // ② 不重叠就跳过
            continue;

        ap->dev = NULL;          /* detach from device */        // ③ 标记已卸载
        list_del(&ap->lh);
        ap->detach(dev);                                        // ④ 调用注册时给的卸载回调
    }

    mutex_unlock(&apertures_lock);
}
```

核心三件事：

- 遍历全局 `apertures` 链表（所有"占有 framebuffer 物理范围"的设备）
- 用 `overlap()` 判断是否落在要清理的范围内
- 调用注册时挂上去的 `ap->detach(dev)` 回调进行真正的"卸载"

### 第 3 层：关键数据结构 `struct aperture_range`

```c
struct aperture_range {
    struct device *dev;                  // 占用这段显存的设备
    resource_size_t base;                // 起始物理地址
    resource_size_t size;                // 大小
    struct list_head lh;                 // 挂到全局 apertures 链表的节点
    void (*detach)(struct device *dev);  // 卸载回调（关键!）
};

static LIST_HEAD(apertures);             // 全局链表头
static DEFINE_MUTEX(apertures_lock);     // 保护链表
```

这是**整个 aperture 子系统的核心数据结构**——理解它就理解了机制：

- 每个占用 framebuffer 的驱动，在注册时往全局链表里挂一个 `aperture_range`
- 后来者要踢它们时，遍历这个链表逐个调 `detach()`

### 第 4 层：`detach` 回调从哪里来？—— 注册侧

需要回头看"占位设备是怎么注册进来的"：

```c
int devm_aperture_acquire_for_platform_device(struct platform_device *pdev,
                                              resource_size_t base,
                                              resource_size_t size)
{
    return devm_aperture_acquire(&pdev->dev, base, size,
                                 aperture_detach_platform_device);  // ← 注册 detach 回调
}
```

而 `aperture_detach_platform_device` 真正的卸载动作就是：

```c
static void aperture_detach_platform_device(struct device *dev)
{
    struct platform_device *pdev = to_platform_device(dev);
    platform_device_unregister(pdev);   // 把平台设备从内核注销
}
```

`devm_aperture_acquire` 则把信息打包成 `aperture_range`，挂到全局链表：

```c
ap->dev    = dev;
ap->base   = base;
ap->size   = size;
ap->detach = detach;
list_add(&ap->lh, &apertures);
```

```text
   │
   ▼
该占位驱动 probe 时调用：
   devm_aperture_acquire_for_platform_device(pdev, fb_base, fb_size)
   │
   ▼
往全局 apertures[] 链表挂一个 aperture_range：
   { dev=pdev, base=fb_base, size=fb_size,
     detach=aperture_detach_platform_device }
   │
   ▼ … 系统正常运行，屏幕显示 EFI 的内容 …
   │
   ▼ 当 linlon-dp 驱动加载时：
linlondp_bind()
   └─ aperture_remove_all_conflicting_devices("linlondp")
        └─ aperture_remove_conflicting_devices(0, -1, "linlondp")
             ├─ sysfb_disable(NULL)         (防止再创建新占位)
             └─ aperture_detach_devices(0, -1)
                  └─ 遍历 apertures[]

   │
   ▼
linlon-dp 安全接管显存，开始自己的 KMS 初始化
```

### 一句话总结

`aperture_remove_all_conflicting_devices` = "**遍历内核里所有声明占用过 framebuffer 物理内存的设备，把和指定地址范围重叠的，统统调用它们注册时留下的 detach 回调进行卸载**"。是 DRM 驱动 probe 时的标准"清场"动作。

### 技巧 2：第一次跳容易掉进 inline 包装/头文件

## 一、回到 inline 包装

```c
static inline int aperture_remove_all_conflicting_devices(const char *name)
```

- 第 2 个参数 `(resource_size_t)-1`：**这就是关键**——把 `-1` 强制转成 `resource_size_t` 类型

## 二、`(resource_size_t)-1` 等于什么？

### 类型链

按你定位到的：

```c
#ifdef CONFIG_PHYS_ADDR_T_64BIT
typedef u64 phys_addr_t;       // = unsigned 64-bit
#else
typedef u32 phys_addr_t;       // = unsigned 32-bit
#endif

typedef phys_addr_t resource_size_t;
```

所以 `resource_size_t` 是**无符号整数**（u32 或 u64），由 `CONFIG_PHYS_ADDR_T_64BIT` 决定宽度。

### `-1` 转成无符号会变成什么

C 标准规定：**有符号 `-1` 转成无符号整型 T，结果是 T 类型的最大值**（也就是所有 bit 全为 1）。

```c
(u32)-1  →  0xFFFFFFFF              = 4 294 967 295        = 2^32 - 1
(u64)-1  →  0xFFFFFFFFFFFFFFFF      = 18 446 744 073 709 551 615 = 2^64 - 1
```

二进制视角：

```
-1 (补码) =  1111...1111
强转无符号  →  保留这些 bit
           →  所有位为 1，即该类型最大值
```

### 所以这里的 size 实际值

- 64-bit 系统：`size = 0xFFFFFFFFFFFFFFFF`
- 32-bit 系统：`size = 0xFFFFFFFF`

## 三、为什么这就"覆盖整个物理地址空间"

在 `aperture_remove_conflicting_devices` → `aperture_detach_devices` 里：

```c
resource_size_t end = base + size;   // 0 + (~0) → 因为无符号溢出，end 也变成 ~0
```

然后用 `overlap(base, end, ap->base, ap->base + ap->size)` 判断范围重叠：

```c
static bool overlap(resource_size_t base1, resource_size_t end1,
                    resource_size_t base2, resource_size_t end2)
{
    return (base1 < end2) && (end1 > base2);
}
```

- `base1 = 0`，`end1 = 最大值`
- 对任何合法的 `ap->base / ap->size`：
  - `0 < end2` 几乎总成立（除非 end2 也是 0）
  - `最大值 > base2` 总成立

**结果：跟任何一个已注册的 aperture_range 都会"重叠"，全部命中、全部 detach。**

这就是"覆盖整个物理地址空间"的含义——不是真的有这么大物理内存，而是构造一个**逻辑上无所不包**的区间，让 overlap 判断对任何已注册条目都返回 true。

## 四、为什么我前面写成 `[0, ~0]`

`~0` 在 C 里是**按位取反 0**，结果也是"所有 bit 为 1"，和 `(unsigned T)-1` 数值上等价。它是讨论"全 1 值"时的口语化简写：

```c
~0         // int 类型的 -1，bit 全 1
~0U        // unsigned int 的最大值
(T)-1      // 类型 T 的最大值（推荐写法，类型明确）
```

内核源码里更严谨地用 `(resource_size_t)-1`，因为：

1. 类型显式，不依赖 `~` 的整型提升规则
2. 不论 `resource_size_t` 是 u32 还是 u64，都能正确得到该类型最大值
3. 比写 `0xFFFFFFFFFFFFFFFFULL` 之类的字面量更通用、更可移植

## 五、扩展：内核里这种写法非常常见

类似套路你会反复见到：

```c
#define U32_MAX   ((u32)~0U)         // include/linux/limits.h
#define U64_MAX   ((u64)~0ULL)
#define ULONG_MAX (~0UL)
#define SIZE_MAX  (~(size_t)0)

memset(buf, 0xff, n);                  // 把内存全填 1
ioremap(addr, (size_t)-1);             // 类似"最大"用法
```

记住这条规则：

> **`(无符号类型 T)-1` ≡ T 的最大值 ≡ T 所有 bit 为 1**
