## 🔗 子系统间的关联

在实际的 SoC bringup 中，这三个子系统往往**紧密耦合**：

### 1. GIC ↔ SCMI

```
SCP 处理完 SCMI 请求 → 发送门铃中断 → GIC 接收中断
    ↓
gic_handle_irq() → cix_mbox_isr() → scmi_rx_callback()
    ↓
complete(&xfer->done) → 唤醒等待的 do_xfer()
```

**关键依赖**：
- SCMI 的响应依赖 GIC 正确路由 mailbox 中断
- 中断优先级设置会影响 SCMI 响应延迟
- 级联中断控制器（如 PDC）可能影响中断送达

### 2. GIC ↔ DRM

```
DPU VBLANK 中断 → GIC → Linux → drm_crtc_handle_vblank()
    ↓
PageFlip 完成事件 → 发送给用户态合成器
```

**关键依赖**：
- VBLANK 中断是整个显示流水线的节拍器
- 中断丢失 = 画面卡住 / PageFlip 超时
- DRM event 机制依赖中断唤醒

### 3. SCMI ↔ DRM

```
Weston 改频率 → clk_set_rate() → scmi_clock_rate_set()
    ↓
do_xfer() → 门铃 → SCP → 配置 PLL → 返回 ACK
```

**关键依赖**：
- DRM 显示控制器的时钟/电源/复位 通常通过 SCMI 控制
- SCMI 超时会导致 DRM atomic commit 卡住
- CIX Sky1 上 linlon-dp 的 `clk_enable` 走 SCMI clock 协议

## 🎯 Bringup 调试优先级（Xen 场景）

在 Xen 下调显示时，按这个顺序逐层验证：

| 阶段 | 验证内容 | 对应子系统 |
|------|----------|------------|
| **1** | GIC 中断是否正确路由到 dom0 | GIC |
| **2** | SCMI mailbox 能否通信、clock 能否设置 | SCMI |
| **3** | DPU 驱动能否 probe、IRQ 是否正常 | GIC + DRM |
| **4** | GOP framebuffer 能否映射 | SCMI (GOP) + Xen P2M |
| **5** | Weston 能否正常 atomic commit | DRM |

## 📖 学习建议

### 初学者路径（从易到难）

1. **先学 GIC**
   - 概念相对独立，异常模型清晰
   - 调试手段直接：看 `/proc/interrupts` + 数计数
   - 代码路径短：`gic_handle_irq` → 设备 handler

2. **再学 SCMI**
   - 四层模型清晰，每层职责明确
   - 核心数据结构 `scmi_xfer` 是理解整个协议栈的钥匙
   - 调试可通过 dump shmem 状态定位问题在哪一层

3. **最后学 DRM**
   - 概念最多（5 个 KMS 对象 + atomic + GEM + ...）
   - 代码量大，涉及用户态 ↔ 内核态交互
   - 但有 `modetest`、`debugfs`、`ftrace` 等丰富工具

### 调试通用技巧

1. **由外向内**：先看 sysfs/debugfs 状态，再打 trace，最后加 print 钻代码
2. **ftrace 优先**：`trace_scmi_*`、`trace_drm_*` 零开销不扰动时序
3. **内存 ring buffer**：串口 print 会拖慢时序，用内存记录事后回读
4. **状态机思维**：中断、xfer、atomic state 本质都是状态机，先画状态转移图
